1. Syntax

1.1. Identifiers

Identifiers (id) are the basic naming unit of the language, used to name variables, types, functions, and relations throughout a specification. Atoms are indivisible symbolic constants that serve as constructor tags or literal markers in type and value definitions. Mixop fragments are the building blocks of mixfix operators, which interleave keyword components with syntactic arguments to form compound notational forms such as if _ then _ else _.

id = text

atom = text

mixop = atom**

1.2. Types

The type system classifies expressions and values in the language. Numeric types (numtyp) distinguish natural numbers (NAT) and integers (INT). Literal types (optyp) extend numeric types with booleans (BOOL) and text strings (TEXT); these are the types of values that can be written as literals. Compound types (typ) include literal types, named user-defined types (VAR, applied to optional type arguments), tuples (TUP), and iterated types (ITER); lists and optional values are encoded as iterated types (ITER typ STAR and ITER typ QUEST, respectively). There is also an opaque function type (FUNC). Definition types (deftyp) describe the shape of user-defined type declarations: a type alias (ALIAS) names an existing type; a struct type (STRUCT) is a product of named fields (typfield); a variant type (VARIANT) is a sum of labeled alternatives (typcase).

numtyp
   : NAT
   | INT
   ;

optyp
   : BOOL
   | numtyp
   | TEXT
   ;

typ
   : optyp
   | VAR id targ*
   | TUP typ*
   | ITER typ iter
   | FUNC
   ;

deftyp
   : ALIAS typ
   | STRUCT typfield*
   | VARIANT typcase*
   ;

typfield
   : atom typ
   ;

typcase
   : mixop typ*
   ;

1.3. Iterators

An iterator (iter) marks a binding or expression as either optional (?) or list-valued (*). Iterators appear on expressions, premises, and arguments to express that a rule applies element-wise across a sequence or an optional value. The bound variable names track which dimensions participate in a given iteration step, and are used by the sub-context machinery to distribute and collect values across iterations.

iter
   : QUEST
   | STAR
   ;

1.4. Variables

A variable reference (vari) consists of an identifier, a type annotation, and zero or more iterator markers (? or ). The type annotation is present for disambiguation during elaboration: distinct occurrences of the same identifier with different types are treated as separate variables. The effective lookup key used at runtime is varr = id iter, which retains the identifier and iterator markers but strips the type annotation.

vari
   : id typ iter*
   ;

1.5. Operators

Operators are the primitive computations applied to values in expressions. They are partitioned into unary, binary, and comparison forms according to their arity and the type of result they produce.

unop
   : boolunop
   | numunop
   ;

binop
   : boolbinop
   | numbinop
   ;

cmpop
   : polycmpop
   | numcmpop
   ;

1.5.1. Boolean operators

Boolean unary operators include logical negation. Boolean binary operators include conjunction and disjunction. These operators are the building blocks of guard conditions used throughout the semantic rules.

boolunop
   : NOT
   ;

boolbinop
   : AND
   | OR
   | IMPL
   | EQUIV
   ;

1.5.2. Numeric operators

Numeric unary operators include sign coercion (PLUS) and arithmetic negation (MINUS). Numeric binary operators include addition, subtraction, multiplication, division, modulo, and exponentiation.

numunop
   : PLUS
   | MINUS
   ;

numbinop
   : ADD
   | SUB
   | MUL
   | DIV
   | MOD
   | POW
   ;

1.5.3. Comparison operators

Comparison operators consume two operands and produce a boolean result. Numeric comparison operators (numcmpop) apply to pairs of integers and provide the usual relational orderings. Polymorphic comparison operators (polycmpop) apply to any pair of values of a compatible type and provide structural equality and inequality tests.

numcmpop
   : LT
   | GT
   | LE
   | GE
   ;

polycmpop
   : EQ
   | NE
   ;

1.6. Values

A value is the fully-evaluated result of an expression. Numeric values (num) are either a natural number (NAT nat) or an integer (INT int). Compound values (val) encompass all value forms: booleans, numeric values, text strings, struct values (STR), union-case injections (INJ), tuples (TUP), optional values (OPT), lists (LIST), function values (FUNC id), and external values (EXT) represented as opaque JSON. Struct values are assembled from named fields (valfield); injection values pair a constructor label with zero or more payload values (valcase).

num
   : NAT nat
   | INT int
   ;

val
   : BOOL bool
   | num
   | TEXT text
   | STR valfield*
   | INJ valcase
   | TUP val*
   | OPT val?
   | LIST val*
   | FUNC id
   | EXT json
   ;

valfield
   : atom val
   ;

valcase
   : mixop val*
   ;

1.7. Expressions

Expressions are the core computational terms of the language. They include literal constants, variable references, unary and binary operations, comparisons, type casts, runtime type tests, and constructors for tuples, structs, cases, options, and lists. Expressions also encompass path-based accesses and updates into structured values, function calls, and iterated forms. An iterator expression (iterexp) annotates an expression with an iterator dimension. Patterns extend expression syntax with destructuring forms used as assignment targets on the left-hand side of let premises.

exp
   : BOOL bool
   | num
   | TEXT text
   | VAR id
   | UN unop exp
   | BIN binop exp exp
   | CMP cmpop exp exp
   | UPCAST typ exp
   | DOWNCAST typ exp
   | SUB exp typ
   | MATCH exp pattern
   | TUP exp*
   | INJ expcase
   | STR expfield*
   | OPT exp?
   | LIST exp*
   | CONS exp exp
   | CAT exp exp
   | MEM exp exp
   | LEN exp
   | DOT exp atom
   | IDX exp exp
   | SLICE exp exp exp
   | UPD exp path exp
   | CALL id targ* arg*
   | ITER exp iterexp
   ;

expcase
   : mixop exp*
   ;

expfield
   : atom exp
   ;

iterexp
   : iter vari*
   ;

1.7.1. Patterns

Patterns are used as the second argument of the MATCH expression, which checks whether a value has a particular shape and returns a boolean. List patterns (listpattern) test whether a list is non-empty (CONS), has exactly n elements (FIXED n), or is empty (NIL). Option patterns (optpattern) test whether an optional value is present (SOME) or absent (NONE). A pattern (pattern) additionally includes an injection match (INJ mixop) that tests whether a union-case value was constructed with a specific constructor label.

listpattern
   : CONS
   | FIXED nat
   | NIL
   ;

optpattern
   : SOME
   | NONE
   ;

pattern
   : INJ mixop
   | listpattern
   | optpattern
   ;

1.7.2. Paths

A path (path) describes a chained sequence of accesses into a structured value: a dot projection to a named struct field, an index into a list by position, or a slice extracting a contiguous sub-sequence. Paths appear in both read access expressions and update expressions, where they identify the sub-value to be replaced.

path
   : ROOT
   | IDX path exp
   | SLICE path exp exp
   | DOT path atom
   ;

1.8. Arguments

Arguments are the actual values and functions supplied at a call site when invoking a function. A type argument (targ) instantiates a type parameter of a polymorphic function with a concrete type. A value argument (arg) is either an expression argument supplying a concrete value for an expression parameter, or a function argument passing a named function for a higher-order parameter.

targ = typ

arg
   : EXP exp
   | FUN id
   ;

1.9. Parameters

Parameters are the formal declarations in a function or relation signature, mirroring the argument forms on the call side. An expression parameter (EXP) binds a typed variable that will receive a value argument at the call site. A function parameter (FUN) binds a higher-order function name with its full type signature, to be supplied by a function argument.

tparam = id

param
   : EXP typ
   | FUN id : tparam* param* -> typ
   ;

1.10. Premises

A premise (prem) is a condition or binding step that guards or extends the context within a rule body. Relation premises (REL) invoke a named relation on input expressions and bind the output expressions to the results. If premises (IF) assert that a boolean expression evaluates to true; the rule fails if it evaluates to false. If-hold and if-not-hold premises (IFHOLD/IFNOTHOLD) assert that a relation call succeeds or fails without consuming its output. Let premises (LET) evaluate an expression and destructure the result into a pattern, extending the context with new bindings. Iterator premises (ITER) apply a premise element-wise across a sequence or optional value. Debug premises (DEBUG) emit a diagnostic value without affecting the context.

prem
   : REL id : exp* -> exp*
   | IF exp
   | IFHOLD id : exp*
   | IFNOTHOLD id : exp*
   | LET exp = exp
   | ITER prem iterprem
   | DEBUG exp
   ;

iterprem
   : iter vari* vari*
   ;

1.11. Definitions

A definition (defn) is a top-level declaration in a specification script. Definitions include external type declarations (EXTTYP), user-defined type definitions (TYP), external and user-defined relation declarations (EXTREL, REL), external and built-in function declarations (EXTFUNC, BUILTINFUNC), table functions (TABLEFUNC), and user-defined functions (FUNC). Each form binds a name in the global environment that may be referred to by subsequent definitions.

defn
   : EXTTYP id
   | TYP id tparam* = deftyp
   | EXTREL id : typ* -> typ*
   | REL id : typ* -> typ* = rulgroup* elsgroup?
   | EXTFUNC id tparam* param* : typ
   | BUILTINFUNC id tparam* param* : typ
   | TABLEFUNC id param* : typ = tblrow*
   | FUNC id tparam* param* : typ = clause* elsclause?
   ;

1.11.1. Rules

A user-defined relation body is organized as a collection of rule groups (rulgroup). Each rule group specifies a match head (rulmatch) consisting of input patterns and guarding premises, together with one or more rule paths (rulpath) that bind output variables and apply additional premises to determine the result. An else group (elsgroup) provides a single fallback path that applies when no earlier rule group’s head matches. This structure supports the case analysis common in formal operational semantics.

rulgroup
   : id : rulmatch = rulpath*
   ;

elsgroup
   : id : rulmatch = rulpath
   ;

rulmatch
   : exp* - prem*
   ;

rulpath
   : id = exp* - prem*
   ;

1.11.2. Clauses

A user-defined function body is organized as an ordered list of clauses (clause). Each clause specifies argument patterns and guarding premises; when the patterns match the actual arguments and all premises succeed, the clause’s result expression is returned. An else clause (elsclause) acts as the final fallback when no earlier clause matches, typically encoding the default or error case.

clause
   : arg* = exp - prem*
   ;

elsclause = clause

1.11.3. Table rows

A table function body is organized as an ordered list of table rows (tblrow). Each row matches against the function arguments and, after evaluating its premises, returns a result expression. Table functions are a special form of user-defined function whose cases are presented in a flat tabular layout; semantically they behave identically to clause-based functions.

tblrow
   : arg* = exp - prem*
   ;

1.12. Scripts

A script (script) is a sequence of top-level definitions forming a complete specification module. Definitions are loaded in order, and each definition may reference only names that have been declared earlier in the same script or in previously loaded scripts. The script is the unit of input to the interpreter’s loading phase.

script = defn*

2. Semantics

2.1. Context

A context holds the environments used for evaluation. It consists of two layers, global and local, each holding four environments: a value environment for variable bindings (venv), a type definition environment (tdenv), a function definition environment (fenv), and a relation definition environment (renv). The global layer is populated once during the loading phase and remains constant throughout evaluation; the local layer is created fresh at each function or relation call and discarded upon return. Variable values are looked up only in the local layer; type and function definitions are looked up in the local layer first, falling back to the global layer if not found there.

layer = {
  TYP tdenv,
  REL renv,
  FUNC fenv,
  VAL venv
}
tdenv = map<id, typdef>

renv = map<id, reldef>

fenv = map<id, funcdef>

venv = map<varr, val>

2.1.1. Loading a context

Before evaluation can begin, a context must be loaded from the specification script. Loading iterates over all definitions in the script and registers each one in the appropriate environment of the global layer. Type definitions, relation definitions, and function definitions are loaded by separate helper functions that translate each definition form into its runtime representation and insert it into the context under the definition’s identifier.

C with script defn* loaded

  1. If let defnh :: defnt* be defn*:

    1. If let EXTTYP id be defnh:

      1. Let C' be C with type EXT loaded as id.

      2. Return C' with script defnt* loaded.

    2. Else if let TYP id tparam* `= deftyp be defnh:

      1. Let C' be C with type DEF tparam* `-> deftyp loaded as id.

      2. Return C' with script defnt* loaded.

    3. Else if let EXTREL id `: typinput* `-> typoutput* be defnh:

      1. Let C' be C with relation EXT id loaded as id.

      2. Return C' with script defnt* loaded.

    4. Else if let REL id `: typinput* `-> typoutput* `= rulgroup* elsgroup? be defnh:

      1. Let C' be C with relation DEF rulgroup* elsgroup? loaded as id.

      2. Return C' with script defnt* loaded.

    5. Else if let EXTFUNC id tparam* param* `: typ be defnh:

      1. Let C' be C with function EXT id loaded as id.

      2. Return C' with script defnt* loaded.

    6. Else if let BUILTINFUNC id tparam* param* `: typ be defnh:

      1. Let C' be C with function BUILTIN id tparam* param* loaded as id.

      2. Return C' with script defnt* loaded.

    7. Else if let TABLEFUNC id param* `: typ `= tblrow* be defnh:

      1. Let C' be C with function TABLE param* `-> tblrow* loaded as id.

      2. Return C' with script defnt* loaded.

    8. Else:

      1. Let FUNC id tparam* param* `: typ `= clause* elsclause? be defnh.

      2. Let C' be C with function DEF tparam* `-> clause* elsclause? loaded as id.

      3. Return C' with script defnt* loaded.

  2. Else:

    1. Return C.

C with type typdef loaded as id

  1. Let tdenvupdate be C.GLOBAL.TYP where id to typdef is added.

  2. Return C with GLOBAL.TYP set to tdenvupdate.

C with relation reldef loaded as id

  1. Let renvupdate be C.GLOBAL.REL where id to reldef is added.

  2. Return C with GLOBAL.REL set to renvupdate.

C with function funcdef loaded as id

  1. Let fenvupdate be C.GLOBAL.FUNC where id to funcdef is added.

  2. Return C with GLOBAL.FUNC set to fenvupdate.

2.1.2. Creating sub-contexts for iteration

When evaluating a premise or expression that is decorated with an iterator (? or *), the evaluator must operate on a collection of sub-contexts, one for each element of the iterated sequence. Each sub-context holds the slice of the current context relevant to a single iteration step. The sub-context creation functions decompose the current context along the bound iteration variables and yield the resulting collection of contexts.

The sub-context of C for optional iterators vari*

  1. Let variiter* be the list obtained by repeating:

    • Let variiter be vari iterated by QUEST.

    for each vari in vari*

  2. Let val'''?* be the list obtained by repeating:

    • Let val'''? be the value of variiter in C.

    for each variiter in variiter*

  3. If val'''? is defined, for all val'''? in val'''?*:

    1. Let val''* be the list obtained by repeating:

      • Let val'' be val'''?.

      for each val'''? in val'''?*

    2. Check that val'' matches pattern OPT %, for all val'' in val''*.

    3. Let val'?* be the list obtained by repeating:

      • Let OPT val'? be val''.

      for each val'' in val''*

    4. Check that val'? is defined, for all val'? in val'?*.

    5. Let val* be the list obtained by repeating:

      • Let val be val'?.

      for each val'? in val'?*

    6. Let ctx be C where each of vari* to each of val* added locally.

    7. Return ctx.

  4. If OPT · is equal to the value of variiter in C, for all variiter in variiter*:

    1. Return ·.

The sub-contexts of C for list iterators vari*

  1. Let variiter* be the list obtained by repeating:

    • Let variiter be vari iterated by STAR.

    for each vari in vari*

  2. Let val''?* be the list obtained by repeating:

    • Let val''? be the value of variiter in C.

    for each variiter in variiter*

  3. Check that val''? is defined, for all val''? in val''?*.

  4. Let val'* be the list obtained by repeating:

    • Let val' be val''?.

    for each val''? in val''?*

  5. Check that val' matches pattern LIST %, for all val' in val'*.

  6. Let val** be the list obtained by repeating:

    • Let LIST val* be val'.

    for each val' in val'*

  7. Let valtrans** be $transpose_<val>(val**).

  8. Let C'* be the list obtained by repeating:

    • Let C' be $sub_list'(C, vari*, valtrans*).

    for each valtrans* in valtrans**

  9. Return C'*.

  2. Else:

An expression is evaluated under a context, producing either a value wrapped in OK or a FAIL result. The central evaluation relation is the following:

  • Evaluating exp under C:

  • Result in res<val>.

If no rule was successfully applied, the evaluation fails:

2.2.1. Boolean, number, and string literals

Literal expressions evaluate to the constant value they denote.

Evaluating exp'' under C:

  1. If let BOOL b be exp'':

    1. Result in OK BOOL b.

  2. Else if let num be exp'':

    1. Result in OK num.

  3. Else:

    1. Let TEXT t be exp''.

    2. Result in OK TEXT t.

2.2.2. Variable references

A variable reference evaluates by looking up the variable’s binding in the local layer of the context. Only the local layer is searched; values are not looked up in the global layer.

Evaluating VAR id under C:

  1. Let val be ! the value of id · in C.

  2. Result in OK val.

2.2.3. Operations

2.2.3.1. Unary expressions

A unary expression evaluates its operand and then applies the unary operator to the resulting value. PLUS coerces the operand to a non-negative number (NAT), and MINUS negates it; both operators work on arbitrary-precision mathematical numbers with no overflow or bit-width constraints.

Evaluating UN unop exp under C:

  1. If unop is equal to NOT:

    1. Let res<val> be

      • the result of evaluating exp under C.

    2. Check that res<val> matches pattern OK %.

    3. Let OK val be res<val>.

    4. Check that val matches pattern BOOL %.

    5. Let BOOL b be val.

    6. Result in OK BOOL ~b.

  2. If let numunop be unop:

    1. Let res<val> be

      • the result of evaluating exp under C.

    2. Check that res<val> matches pattern OK %.

    3. Let OK val be res<val>.

    4. Check that val has type num.

    5. Let num be val.

    6. Let valres be $unop_number(numunop, num).

    7. Result in OK valres.

2.2.3.2. Binary expressions

A binary expression evaluates both operands and applies the binary operator to the pair of resulting values. The numeric operators (ADD, SUB, MUL, DIV, MOD, POW) perform purely mathematical arithmetic on NAT and INT values, backed by arbitrary-precision integers with no overflow.

Evaluating BIN binop expl expr under C:

  1. If let boolbinop be binop:

    1. Let res<val> be

      • the result of evaluating expl under C.

    2. Check that res<val> matches pattern OK %.

    3. Let OK val be res<val>.

    4. Check that val matches pattern BOOL %.

    5. Let BOOL bl be val.

    6. Let res<val>' be

      • the result of evaluating expr under C.

    7. Check that res<val>' matches pattern OK %.

    8. Let OK val' be res<val>'.

    9. Check that val' matches pattern BOOL %.

    10. Let BOOL br be val'.

    11. Let bres be $binop_bool(boolbinop, bl, br).

    12. Result in OK BOOL bres.

  2. Else:

    1. Let numbinop be binop.

    2. Let res<val> be

      • the result of evaluating expl under C.

    3. Check that res<val> matches pattern OK %.

    4. Let OK val be res<val>.

    5. Check that val has type num.

    6. Let numl be val.

    7. Let res<val>' be

      • the result of evaluating expr under C.

    8. Check that res<val>' matches pattern OK %.

    9. Let OK val' be res<val>'.

    10. Check that val' has type num.

    11. Let numr be val'.

    12. Let valres be $binop_number(numbinop, numl, numr).

    13. Result in OK valres.

2.2.3.3. Comparison expressions

A comparison expression evaluates both operands and applies the comparison operator, producing a boolean value. Numeric-ordering operators (LT, GT, LE, GE) compare NAT and INT values by their mathematical ordering. Equality operators (EQ, NE) compare structural representations of any meta-type value; for example, NAT 1 < NAT 2 and STRUCT …​ = STRUCT …​ are both valid comparisons.

Evaluating CMP cmpop expl expr under C:

  1. If let polycmpop be cmpop:

    1. Let res<val> be

      • the result of evaluating expl under C.

    2. Check that res<val> matches pattern OK %.

    3. Let OK vall be res<val>.

    4. Let res<val>' be

      • the result of evaluating expr under C.

    5. Check that res<val>' matches pattern OK %.

    6. Let OK valr be res<val>'.

    7. Let bres be $cmpop_poly(polycmpop, vall, valr).

    8. Result in OK BOOL bres.

  2. Else:

    1. Let numcmpop be cmpop.

    2. Let res<val> be

      • the result of evaluating expl under C.

    3. Check that res<val> matches pattern OK %.

    4. Let OK val be res<val>.

    5. Check that val has type num.

    6. Let numl be val.

    7. Let res<val>' be

      • the result of evaluating expr under C.

    8. Check that res<val>' matches pattern OK %.

    9. Let OK val' be res<val>'.

    10. Check that val' has type num.

    11. Let numr be val'.

    12. Let bres be $cmpop_number(numcmpop, numl, numr).

    13. Result in OK BOOL bres.

2.2.4. Casts

2.2.4.1. Upcast expressions

An upcast expression converts a value toward a more general type. The natural numbers are a subset of the integers, so NAT values can be upcast to INT. For user-defined alias types the alias is unfolded and the upcast is applied recursively. For all other types, the value is returned unchanged if it is already structurally compatible.

Evaluating UPCAST typ exp under C:

  1. Let res<val> be

    • the result of evaluating exp under C.

  2. Check that res<val> matches pattern OK %.

  3. Let OK val be res<val>.

  4. Result in val upcasted to typ under C.

Upcasting is defined as follows:

val' upcasted to typ'' under C

  1. If let numtyp be typ'':

    1. Check that numtyp is INT.

    2. If let num be val':

Call_func_cache: C |- id typ* val* funccache : %

C |- id typ* val* funccache : %:

  1. If let OK valcached be funccache:

    1. Result in OK valcached.

  2. Else:

    1. Let ( cursor, funcdef ) be ! the function definition of id in C.

    3. Let C |- funcdef typ* val* : valres.

    4. Let cpafter be cache checkpoint.

    5. Let bext be funcdef has type externFuncDef.

    6. Let bseff be side-effect occurred between checkpoints cpbefore and cpafter.

    7. Let banon be cursor is equal to LOCAL.

    8. Let bool* be the list obtained by repeating:

      • Let bool be val is a function.

      for each val in val*

The actual function call is performed by the following relation, dispatching according to the function type. The function definition is looked up in the context and its kind determines which evaluation strategy is used.

Call_func_dispatch: C |- funcdef typ* val* : %

  1. If let EXT id be funcdef:

    1. Let valres be

  3. Else if let tableFuncDef be funcdef:

    1. Check that typ* is an empty list.

  4. Else:

    2. Let valres be

2.5.1. Extern functions

Extern functions are declared in the specification but implemented outside of it. Calling an extern function invokes the external implementation registered under its identifier. The specification leaves the semantics of extern functions unspecified at this level.

Call_extern_func:

  • Evaluating extern function id with types typ* and inputs val*:

  • Result in res<val>.

2.5.2. Built-in functions

Built-in functions are primitive operations whose semantics are defined directly in the interpreter, rather than by a specification body. They are looked up by name and applied to their arguments by the interpreter’s built-in dispatch mechanism.

Call_builtin_func: |- id `@ `< typ* > `( val* ) : %

2.5.3. Table functions

A table function is defined by an ordered list of table rows. Each row specifies argument patterns and guarding premises; the function is evaluated by trying the rows in order and returning the result of the first matching row. Table functions present the same behavior as clause-based functions but use a flat tabular layout for readability.

Call_table_func:

  • Evaluating tableFuncDef with inputs val* under C:

  • Result in res<val>.

Evaluating tableFuncDef with inputs val* under C:

  1. Let TABLE _* `-> tblrow* be tableFuncDef.

  2. Let valres be

    • the result of evaluating tblrow* with inputs val* under C.

  3. Result in valres.

Table rows are evaluated as follows. Each row is tried in order. For each row, a fresh local context is created from the global context, argument assignment is performed for that row’s argument patterns against the actual argument values, and the row’s premises are evaluated. The first row whose argument patterns match and whose premises all succeed provides the result expression.

Eval_tblrows:

  • Evaluating tblrow* with inputs val* under C:

  • Result in res<val>.

Evaluating tblrow* with inputs val* under C:

  1. If tblrow* is an empty list:

    1. Result in FAIL.

  2. Else:

    1. Let tblrowh :: tblrowt* be tblrow*.

    2. Let res<val> be

      • the result of evaluating tblrowh with inputs val* under C.

    3. If let OK valout be res<val>:

      1. Result in OK valout.

    4. Else:

      1. Let valres be

        • the result of evaluating tblrowt* with inputs val* under C.

      2. Result in valres.

Eval_tblrow:

  • Evaluating tblrow with inputs val* under C:

  • Result in res<val>.

Evaluating tblrow with inputs val* under C:

  1. Let arg* `= expout `- prem* be tblrow.

  2. Let Ccallee be C with LOCAL set to $empty_layer.

  3. Let Ccallee `/ C |- arg* := val* : Ccallee'.

  4. Let res<ctx> be

    • the result of evaluating prem* under Ccallee'.

  5. Check that res<ctx> matches pattern OK %.

  6. Let OK Ccallee'' be res<ctx>.

  7. Let res<val> be

    • the result of evaluating expout under Ccallee''.

  8. Check that res<val> matches pattern OK %.

  9. Let OK valout be res<val>.

  10. Result in OK valout.

2.5.4. User-defined functions

A user-defined function is defined by an ordered list of clauses, optionally followed by an else clause. Calling a user-defined function creates a fresh local context from the global context, with the function’s type parameters registered in the type environment so that type-parameter substitution works correctly during evaluation. Argument values are then assigned and clauses are tried in order; the first clause whose argument patterns match the actual arguments and whose premises all succeed provides the result. If no clause matches, the else clause is used as a fallback; if there is none, the call fails.

Call_defined_func:

  • Evaluating definedFuncDef with types typ* and inputs val* under C:

  • Result in res<val>.

Evaluating definedFuncDef with types typ* and inputs val* under C:

  1. Let DEF tparam* `-> clause* elsclause? be definedFuncDef.

  2. Check that the length of tparam* is equal to the length of typ*.

  3. Let tdenv be `{ ( tparam `: DEF · `-> ALIAS typ )* }.

  4. Let Ccallee be C with LOCAL set to $empty_layer[TYP = tdenv].

  5. Let clauseelse* be $opt_as_seq_<clause>(elsclause?).

  6. Let clauseall* be clause* concatenated with clauseelse*.

  7. Let Ccallee `/ C |- clauseall* `@ `( val* ) : valres.

  8. Result in valres.

Function clauses are evaluated as follows. The clause sequence is tried in order. For each clause, argument assignment is attempted; if it succeeds and all premises hold, the result expression is evaluated and returned. Otherwise evaluation moves to the next clause.

Eval_clauses: C `/ Ccaller |- clause* `@ `( val* ) : %

C `/ Ccaller |- clause* `@ `( val* ) : %:

  1. If clause* is an empty list:

    1. Result in FAIL.

  2. Else:

    1. Let clauseh :: clauset* be clause*.

    2. Let C `/ Ccaller |- clauseh `@ `( val* ) : res<val>.

    3. If let OK valres be res<val>:

      1. Result in OK valres.

    4. Else:

      1. Let C `/ Ccaller |- clauset* `@ `( val* ) : valres.

      2. Result in valres.

Eval_clause: C `/ Ccaller |- clause `@ `( val* ) : %

C `/ Ccaller |- clause `@ `( val* ) : %:

  1. Let arg* `= expout `- prem* be clause.

  2. Let C `/ Ccaller |- arg* := val* : C'.

  3. Let res<ctx> be

    • the result of evaluating prem* under C'.

  4. Check that res<ctx> matches pattern OK %.

  5. Let OK C'' be res<ctx>.

  6. Let res<val> be

    • the result of evaluating expout under C''.

  7. Check that res<val> matches pattern OK %.

  8. Let OK valout be res<val>.

  9. Result in OK valout.

2.6. Relations

Relation calls are dispatched through the same layered chain as function calls: a memo cache is checked first for a previously computed result, then the relation definition is resolved from the context, and finally evaluation is dispatched based on whether the relation is extern or user-defined.

An entry point for relation calls is the following relation:

Call_rel:

  • Calling id with arguments val* under C:

  • Result in res<val*>.

Calling id with arguments val* under C:

  1. Let relcache be meta-cache entry for relation id with inputs val*.

  2. Let C |- id val* relcache : valsres.

  3. Result in valsres.

A meta-cache is used for performance reasons. Before evaluating a relation call from scratch, the cache is consulted for a previously computed result with the same identifier and input values. If found, the cached result is returned immediately; otherwise, the result is computed and stored in the cache for future reuse.

Call_rel_cache: C |- id valinput* relcache : %

C |- id valinput* relcache : %:

  1. If let OK valcached* be relcache:

    1. Result in OK valcached*.

  2. Else:

    1. Let reldef be ! the relation definition of id in C.

    2. Let cpbefore be cache checkpoint.

    3. Let C |- reldef valinput* : valsres.

    4. Let cpafter be cache checkpoint.

    5. Let bext be reldef has type externRelDef.

    6. Let bseff be side-effect occurred between checkpoints cpbefore and cpafter.

    7. Check that $cache_add_rel_maybe(bext \/ bseff, id, valinput*, valsres).

    8. Result in valsres.

  1. If let definedRelDef be reldef:

2.6.2. User-defined relations

A user-defined relation is defined by a collection of rule groups, optionally followed by an else group. Calling a user-defined relation attempts each rule group in order, trying all rule paths within the matched group, and returns the first successful result. If no rule group matches, the else group is tried if present; if none matches, the call fails.

Call_defined_rel:

  • Evaluating definedRelDef with inputs val* under C:

  • Result in res<val*>.

Evaluating definedRelDef with inputs val* under C:

  1. Let DEF rulgroup* elsgroup? be definedRelDef.

  2. Let rulgroupels* be the list obtained by repeating:

    • Let rulgroupels be $elsgroup_as_rulgroup(elsgroup).

    for each elsgroup in elsgroup*

  3. Let rulgroup'* be $opt_as_seq_<rulgroup>(rulgroupels?).

  4. Let rulgroupall* be rulgroup* concatenated with rulgroup'*.

  5. Let Clocal be C with LOCAL set to $empty_layer.

  6. Let Clocal |- rulgroupall* `@ `( val* ) : valsres.

  7. Result in valsres.

Rule groups are evaluated as follows. The list of rule groups is tried in order; the first group whose match head (input patterns and guarding premises) applies to the given inputs is evaluated. Within a matching group, the rule paths are tried in order to find a successful result.

  1. If rulgroup* is an empty list:

    1. Result in FAIL.

    4. Else:

      1. Let C |- rulgroupt* `@ `( val* ) : valsres.

      2. Result in valsres.

Eval_rulgroup: C |- rulgroup `@ `( val* ) : %

C |- rulgroup `@ `( val* ) : %:

  4. Let OK valout* be res<val*>.

  5. Result in OK valout*.

Rules are evaluated as follows. Each rule path within a rule group is tried in order. A rule path succeeds when its output expressions can be bound to the values produced by its premises; the first successful path provides the result for the entire rule group.
