# Bugs of K shown by K in P4-SpecTec

K in P4-SpecTec follows the K documentation where the documentation says what
K does. Running it against `krun` therefore shows where K v7.1.337 (LLVM
backend `f02284f`, v0.1.140) does not do what its documentation says. This
file collects ten such places. Each has a test in
`spec-k/tests/manual/behavior/`, listed as `known` in `spec-k/tests/suites.toml`
because K in P4-SpecTec and `krun` are expected to differ on it.

## 1. Fresh values in functions

Diff test: [`tests/manual/behavior/fresh-in-function`](tests/manual/behavior/fresh-in-function/)

A variable `!X` on the right-hand side of a rule stands for a fresh value. The
documentation promises that the value is new
([`kast.md`:172-176](https://github.com/runtimeverification/k/blob/4a46d1231473b599c699160132fd6e76a5c46406/k-distribution/include/kframework/builtin/kast.md?plain=1#L172-L176)):

> refer[s] to a unique value of the specified sort which is distinct from any
> other value that has been generated or will be generated by the `!X` syntax.

`!X` may be used in a rule and in a function equation alike. The test does
both: the rule takes a fresh value `!_X`, and calls a function `fr` that takes
one, twice.

```k
syntax Int ::= fr(Int) [function]
rule fr(_) => !_I:Int
rule <k> alongside(N) => ListItem(!_X:Int) ListItem(fr(N)) ListItem(fr(N)) </k>
```

The three values should all differ, but `krun` gives the rule and the first
call the same value, 0:

| Program | `krun` | K in P4-SpecTec |
|---|---|---|
| `alongside(5)` | `0`, `0`, `1` | `0`, `-1`, `-2` |

Fresh values are counted in the cell `<generatedCounter>`, which starts at 0.
kompile turns the rule of the test into the following (from the kompiled
`definition.kore`, simplified):

```k
rule <generatedTop>
       <k> alongside(N) </k>
       <generatedCounter> C </generatedCounter>
     </generatedTop> #as Config
  => <generatedTop>
       <k> ListItem(freshInt(C +Int 0)) ListItem(fr(N, Config)) ListItem(fr(N, Config)) </k>
       <generatedCounter> C +Int 1 </generatedCounter>
     </generatedTop>
```

`!X` is handled differently in the rule and in the function:

- **In the rule**, kompile replaces `!_X` with the counter `C` of the matched
  configuration (`freshInt(C)` is `C`), and sets the counter to `C + 1`
  ([`ResolveFreshConstants.java`:158-175](https://github.com/runtimeverification/k/blob/4a46d1231473b599c699160132fd6e76a5c46406/k-frontend/src/main/java/org/kframework/compile/ResolveFreshConstants.java#L158-L175)).
- **In the function**, kompile leaves `!X` to the LLVM backend
  ([`ResolveFreshConstants.java`:92-104](https://github.com/runtimeverification/k/blob/4a46d1231473b599c699160132fd6e76a5c46406/k-frontend/src/main/java/org/kframework/compile/ResolveFreshConstants.java#L92-L104)),
  and passes the function the matched configuration `Config`. The backend
  takes the counter of `Config` and increments it in place
  ([`llvm_header.inc`:151-164](https://github.com/runtimeverification/llvm-backend/blob/f02284f09858cd2b9f310ad0142b3e04054295ec/config/llvm_header.inc#L151-L164)).

So `alongside(5)`, with the counter at 0, runs as follows:

1. The rule matches with `C` = 0, so `!_X` is 0.
2. The first `fr(N)` reads the counter of `Config`, which is still 0. It gets
   0 and raises that counter to 1.
3. The second `fr(N)` gets 1.
4. The rule sets the counter to `C + 1` = 1.

[llvm-backend#104](https://github.com/runtimeverification/llvm-backend/issues/104),
which designed this, calls it safe because "no rule is allowed to refer to the
generatedCounter cell directly". The rules that kompile makes for `!X` do.

The bug needs both a rule and a function to take fresh values: calling `fr`
twice from a rule without `!X` gives 0 and 1. K in P4-SpecTec takes the fresh
values of functions below zero (`Eval/fresh` in `4.2-eval.watsup`), so they
never meet those of rules, which count up from zero.

## 2. `choice` on maps

Diff test: [`tests/manual/behavior/choice`](tests/manual/behavior/choice/)

`choice(M)` gives some key of the map `M`. The documentation leaves open which
key, but promises the same key for the same map
([`domains.md`:388-390](https://github.com/runtimeverification/k/blob/4a46d1231473b599c699160132fd6e76a5c46406/k-distribution/include/kframework/builtin/domains.md?plain=1#L388-L390)):

> The same key will always be returned for the same map, but no guarantee is
> given that two different maps will return the same element, even if they are
> similar.

The test builds the map `{5 ↦ 1, -5 ↦ 2}` twice, inserting the keys in
opposite orders. It checks that the two maps are equal by `==K`, and takes
`choice` of each (the last two items are for 3 below):

```k
rule <k> run(N) => ListItem(.Map [ N <- 1 ] [ 0 -Int N <- 2 ] ==K .Map [ 0 -Int N <- 2 ] [ N <- 1 ])
                   ListItem(choice(.Map [ N <- 1 ] [ 0 -Int N <- 2 ]))
                   ListItem(choice(.Map [ 0 -Int N <- 2 ] [ N <- 1 ]))
                   ListItem(Set2List(SetItem(N) SetItem(0 -Int N)))
                   ListItem(Set2List(SetItem(0 -Int N) SetItem(N))) </k>
```

| Program | `krun` | K in P4-SpecTec |
|---|---|---|
| `run(5)` | `true`, `-5`, `5`, … | `true`, `-5`, `-5`, … |

The maps are equal, yet `krun` gives -5 for one and 5 for the other. The LLVM
backend keeps a map as a hash trie, and `choice` returns its first element
([`maps.cpp`:116-121](https://github.com/runtimeverification/llvm-backend/blob/f02284f09858cd2b9f310ad0142b3e04054295ec/runtime/collections/maps.cpp#L116-L121)).
Equal maps would have the same first element if every key had its own place in
the trie. But the hash of an integer is computed from its digits only, without
its sign
([`int.cpp`:369-374](https://github.com/runtimeverification/llvm-backend/blob/f02284f09858cd2b9f310ad0142b3e04054295ec/runtime/arithmetic/int.cpp#L369-L374),
`int_hash`), so 5 and -5 have the same hash, share a place, and are kept in
the order they were inserted. K in P4-SpecTec gives the least key.

## 3. `Set2List`

Diff test: [`tests/manual/behavior/choice`](tests/manual/behavior/choice/)

`Set2List(S)` lists the elements of the set `S` in some order. Again the
documentation leaves the order open but promises the same order for equal sets
([`domains.md`:1056-1058](https://github.com/runtimeverification/k/blob/4a46d1231473b599c699160132fd6e76a5c46406/k-distribution/include/kframework/builtin/domains.md?plain=1#L1056-L1058)):

> Two equal sets are guaranteed to generate the same ordering

The test of 2 also builds the set `{5, -5}` in both orders and lists it:

| Program | `krun` | K in P4-SpecTec |
|---|---|---|
| `run(5)` | …, `[-5, 5]`, `[5, -5]` | …, `[-5, 5]`, `[-5, 5]` |

The cause is the same as in 2: `Set2List` lists the hash trie in order
([`sets.cpp`:96-102](https://github.com/runtimeverification/llvm-backend/blob/f02284f09858cd2b9f310ad0142b3e04054295ec/runtime/collections/sets.cpp#L96-L102)),
and 5 and -5 are in the order they were inserted. K in P4-SpecTec lists a set
in order of value.

## 4. `choice` on range maps

Diff test: [`tests/manual/behavior/rangemap-choice`](tests/manual/behavior/rangemap-choice/)

A range map maps ranges of integers to values, and the documentation promises
of its `choice` what it promises of maps
([`domains.md`:676-677](https://github.com/runtimeverification/k/blob/4a46d1231473b599c699160132fd6e76a5c46406/k-distribution/include/kframework/builtin/domains.md?plain=1#L676-L677)):

> The same key will always be returned for the same range map

The test builds a range map of the four ranges `[1, 2)`, `[3, 4)`, `[5, 6)`,
and `[7, 8)` twice, inserting them in increasing and in decreasing order, and
takes `choice` of each:

| Program | `krun` | K in P4-SpecTec |
|---|---|---|
| `run(1)` | `true`, `3`, `5` | `true`, `1`, `1` |

The LLVM backend keeps a range map as a red-black tree, and `choice` returns
the range at the root
([`rangemaps.cpp`:162-168](https://github.com/runtimeverification/llvm-backend/blob/f02284f09858cd2b9f310ad0142b3e04054295ec/runtime/collections/rangemaps.cpp#L162-L168)).
Which range ends up at the root depends on the order of insertion: `[3, 4)` in
one tree and `[5, 6)` in the other. K in P4-SpecTec gives the least range.

## 5. `updateList` at index 0

Diff test: [`tests/manual/behavior/updatelist-index0`](tests/manual/behavior/updatelist-index0/)

`updateList(L, I, S)` overwrites the elements of the list `L` from index `I`
on with the list `S`. If `S` does not fit, the documentation says it fails
([`domains.md`:995](https://github.com/runtimeverification/k/blob/4a46d1231473b599c699160132fd6e76a5c46406/k-distribution/include/kframework/builtin/domains.md?plain=1#L995)):

> Having `index + N > K` yields an exception.

where `N` is the length of `S` and `K` that of `L`. The test writes 3 elements,
and then 40, at index 0 of a list of one element:

```k
rule <k> short(N) => updateList(ListItem(N), 0, ListItem(1) ListItem(2) ListItem(3)) </k>
rule <k> long(N) => size(updateList(ListItem(N), 0, makeList(40, N))) </k>
```

| Program | `krun` | K in P4-SpecTec |
|---|---|---|
| `short(7)` | `ListItem(1)` | fails |
| `long(7)` | `40` | fails |

Both should fail, but `krun` gives a result, and not even the same kind of
result: with 3 elements the list keeps its length 1 and loses 2 and 3, and
with 40 it grows to 40. The LLVM backend checks that `S` fits only when `I` is
not 0
([`lists.cpp`:181-188](https://github.com/runtimeverification/llvm-backend/blob/f02284f09858cd2b9f310ad0142b3e04054295ec/runtime/collections/lists.cpp#L181-L188)).

## 6. `String2Int` and `String2Base`

Diff test: [`tests/manual/behavior/string2int-syntax`](tests/manual/behavior/string2int-syntax/)

`String2Int(S)` reads an integer from a string, and `String2Base(S, R)` reads
one in radix `R`. The documentation says which strings and radixes they take
([`domains.md`:1820-1828](https://github.com/runtimeverification/k/blob/4a46d1231473b599c699160132fd6e76a5c46406/k-distribution/include/kframework/builtin/domains.md?plain=1#L1820-L1828)):

> The String will be represented in the syntax of the `INT` module (i.e., a
> nonempty sequence of digits optionally prefixed by a sign). […] This radix
> can be anywhere between 2 and 36.

The test gives a string with spaces, and a radix of 37:

| Program | `krun` | K in P4-SpecTec |
|---|---|---|
| `int(" 1 23")` | `123` | fails |
| `base("10", 37)` | `37` | fails |

The LLVM backend drops a leading `+` and passes the string to the GMP function
`mpz_init_set_str`
([`strings.cpp`:214-235](https://github.com/runtimeverification/llvm-backend/blob/f02284f09858cd2b9f310ad0142b3e04054295ec/runtime/strings/strings.cpp#L214-L235)),
which has its own syntax: it skips white space anywhere in the string, and
takes radixes up to 62.

## 7. `padRightBytes`

Diff test: [`tests/manual/behavior/padright-value`](tests/manual/behavior/padright-value/)

`padRightBytes(B, N, V)` pads the bytes `B` on the right with the byte `V` up
to length `N`. A byte is at most 255, and the documentation says other values
fail
([`domains.md`:2176-2177](https://github.com/runtimeverification/k/blob/4a46d1231473b599c699160132fd6e76a5c46406/k-distribution/include/kframework/builtin/domains.md?plain=1#L2176-L2177)):

> The result is `#False` if `value` is not in the range `[0..255]`, or if the
> length is negative.

The test pads two bytes to length 1 with the value 999. No byte needs to be
added, but the value is not a byte:

```k
rule <k> run(V) => padRightBytes(Int2Bytes(2, 258, BE), 1, V) </k>
```

| Program | `krun` | K in P4-SpecTec |
|---|---|---|
| `run(999)` | `b"\x01\x02"` | fails |

The LLVM backend returns the bytes as they are when they are long enough, and
checks the value only after that
([`bytes.cpp`:338-342](https://github.com/runtimeverification/llvm-backend/blob/f02284f09858cd2b9f310ad0142b3e04054295ec/runtime/strings/bytes.cpp#L338-L342)).
`padLeftBytes` is written the same way
([`bytes.cpp`:369-373](https://github.com/runtimeverification/llvm-backend/blob/f02284f09858cd2b9f310ad0142b3e04054295ec/runtime/strings/bytes.cpp#L369-L373)),
though the test covers only `padRightBytes`.

## 8. `^%Int` with a negative exponent

Diff test: [`tests/manual/behavior/powmod`](tests/manual/behavior/powmod/)

`A ^%Int B C` raises `A` to the power `B` modulo `C`. The documentation defines
it by `^Int` and `%Int`
([`domains.md`:1229-1231](https://github.com/runtimeverification/k/blob/4a46d1231473b599c699160132fd6e76a5c46406/k-distribution/include/kframework/builtin/domains.md?plain=1#L1229-L1231)):

> `A ^%Int B C` is equal in value to `(A ^Int B) %Int C`, but has a better
> asymptotic complexity.

`2 ^Int -1` has no value in `krun`: it stops with `Exponent out of range: 2 ^
-1` (the test `tests/manual/errors/pow`). So `(2 ^Int -1) %Int 5` has none
either, and neither should `2 ^%Int -1 5`. The test computes it:

```k
rule <k> run(B, C) => 2 ^%Int B C </k>
```

| Program | `krun` | K in P4-SpecTec |
|---|---|---|
| `run(-1, 5)` | `3` | fails |

`krun` gives 3, the inverse of 2 modulo 5. For a negative exponent the LLVM
backend takes the modular inverse (GMP `mpz_powm`), while `^Int` rejects any
exponent that is not a nonnegative machine integer
([`int.cpp`:159-185](https://github.com/runtimeverification/llvm-backend/blob/f02284f09858cd2b9f310ad0142b3e04054295ec/runtime/arithmetic/int.cpp#L159-L185)).
The two sides of the documented equation thus differ in `krun` itself. K in
P4-SpecTec fails on a negative exponent, as `^Int` does.

## 9. Overlapping occurrences in strings

Diff test: [`tests/manual/behavior/overlapping-occurrences`](tests/manual/behavior/overlapping-occurrences/)

`countAllOccurrences(S, A)` counts the occurrences of `A` in `S`, and
`replaceAll(S, A, B)` replaces them with `B`. In `"aaa"`, `"aa"` occurs at
index 0 and, overlapping it, at index 1. The documentation defines both
functions by equations
([`domains.md`:1896-1917](https://github.com/runtimeverification/k/blob/4a46d1231473b599c699160132fd6e76a5c46406/k-distribution/include/kframework/builtin/domains.md?plain=1#L1896-L1917)),
which count an occurrence and go on after its end, so occurrences do not
overlap:

```k
rule countAllOccurrences(Source:String, ToCount:String) => 1 +Int countAllOccurrences(substrString(Source, findString(Source, ToCount, 0) +Int lengthString(ToCount), lengthString(Source)), ToCount)
          requires findString(Source, ToCount, 0) >=Int 0
rule replaceAll(Source:String, ToReplace:String, Replacement:String) => replace(Source, ToReplace, Replacement, countAllOccurrences(Source, ToReplace))
```

By these equations, `"aaa"` has one occurrence of `"aa"`, and replacing it with
`"b"` gives `"ba"`. The functions are hooked, so `krun` does not use the
equations, but they state what the hooks should do; as
[runtimeverification/k#3896](https://github.com/runtimeverification/k/issues/3896)
says of them, they "exist to document the expected behavior of hooked
functions". The test runs both functions on such strings:

| Program | `krun` | K in P4-SpecTec |
|---|---|---|
| `count("aaa", "aa")` | `2` | `1` |
| `replace("aaa", "aa", "b")` | `"b"` | `"ba"` |
| `replace("aaaaaaa", "aa", "b")` | `"b"` | `"bbba"` |
| `replace("aaa", "aa", "xyz")` | `"xyzxy"` | `"xyza"` |

After an occurrence, the LLVM backend searches on from the next character, not
from the end of the occurrence
([`strings.cpp`:299](https://github.com/runtimeverification/llvm-backend/blob/f02284f09858cd2b9f310ad0142b3e04054295ec/runtime/strings/strings.cpp#L299)
and [356](https://github.com/runtimeverification/llvm-backend/blob/f02284f09858cd2b9f310ad0142b3e04054295ec/runtime/strings/strings.cpp#L356)),
so it counts 2. `replaceAll` is worse than counting overlaps: it takes the two
overlapping occurrences, computes the length of the result as if they did not
overlap, 3 − 2 × (2 − 1) = 1, and copies until that length
([`strings.cpp`:305-327](https://github.com/runtimeverification/llvm-backend/blob/f02284f09858cd2b9f310ad0142b3e04054295ec/runtime/strings/strings.cpp#L305-L327)).
So `"aaa"` becomes `"b"`, all of `"aaaaaaa"` becomes one `"b"`, and with the
longer replacement `"xyz"` the result is cut in the middle, `"xyzxy"`. These
results are wrong even if occurrences were meant to overlap.

## 10. `Float` literals beyond the exponent range

Diff test: [`tests/manual/behavior/float-literal-range`](tests/manual/behavior/float-literal-range/)

A `Float` literal is rounded to the format its suffix names; without a suffix,
the format is IEEE 754 `binary64` (`double`). The documentation says the
rounding respects both the precision and the exponent range of the format
([`domains.md`:1478-1483](https://github.com/runtimeverification/k/blob/4a46d1231473b599c699160132fd6e76a5c46406/k-distribution/include/kframework/builtin/domains.md?plain=1#L1478-L1483)):

> Finally, it is rounded to the nearest possible value in a floating-point type
> represented like an IEEE754 floating-point type, with the number of bits of
> precision and exponent specified by the suffix.

The largest finite `binary64` is about 1.8e308, so the literal `1.0e400` should
round to infinity, as it does in C:

```k
rule <k> run() => 1.0e400 </k>
```

| Program | `krun` | K in P4-SpecTec |
|---|---|---|
| `run()` | `0.99999999999999997e400` | `Infinity` |

`krun` keeps a finite number that no `binary64` can hold. The LLVM backend
rounds the literal to the precision of the format, 53 bits, but within MPFR's
default exponent range, which is far wider than that of `binary64`
([`CreateStaticTerm.cpp`:214-248](https://github.com/runtimeverification/llvm-backend/blob/f02284f09858cd2b9f310ad0142b3e04054295ec/lib/codegen/CreateStaticTerm.cpp#L214-L248)).
The exponent bits of the format are only stored along with the value.
